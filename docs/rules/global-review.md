# 全局审查规则

## 证据原则

- 只基于需求、源码和 diff 中的直接证据下结论，不得臆造未出现的事实。
- 不猜测外部接口行为、未知运行环境、未提供的依赖或部署细节。
- 正式问题必须给出文件、起止行、可核对的代码证据、根因、影响和只读修复建议。
- 工具告警只是候选，必须结合控制流和调用链确认后才能成为问题；不得伪造工具结果。
- 同一根因只报告一次。连锁后果写入证据，不为同一根因拆多条问题。
- “可能、猜测、推测”不能写成已确认的中高风险结论。证据不足就不报中高风险。

## 审查优先级

优先发现并报告以下问题：

- 正确性
- 安全性
- 内存安全
- 并发正确性
- 资源生命周期

## 正确性与控制流

- 检查类型不匹配、缺失返回值、空值、未初始化、越界、除零、溢出、恒真或恒假条件、不可达路径。
- 检查 `return`、`break`、`continue`、`goto` 是否跳过清理、状态推进、计数或错误传播。
- 检查成功、部分成功、EOF、重试、取消和异常路径是否仍满足调用契约。

## 安全与权限

只在代码里能看到入口、数据流和影响时报告：

- 注入、未授权访问、越权、路径穿越、不安全反序列化。
- 敏感信息写入日志，以及硬编码凭据。

未知的外部鉴权或部署行为不作为已确认问题。

## 内存与资源

追踪文件描述符、socket、锁、线程、连接、动态对象、缓存、回调、映射和第三方句柄的获取与释放。检查泄漏、重复释放、悬空引用、use-after-free、错误路径未清理，以及只增不删的缓存或缺少容量上限。

## 并发与稳定性

- 检查数据竞争、非线程安全集合、锁顺序、死锁、锁内阻塞调用、线程膨胀。
- 检查回调生命周期：取消后的迟到回调、回调移除时仍在执行、重复回调是否幂等。
- 检查队列、重连、重试、日志、任务和缓存是否有容量、退避、超时和停止条件。失败不能形成无退避的重试风暴。

## 数据、事务与接口

- 检查多表或多对象更新是否原子，失败时是否回滚或补偿。
- 检查状态机不变量，以及生产者与消费者、Schema、代码和接口字段是否一致。
- 金额、数量、费率、时间和单位必须使用匹配的类型、精度、边界和舍入。具体业务口径以需求或 checklist 中的证据为准，不得臆造。

## 性能

只在 diff、数据规模、调用频率或明确热点路径提供证据时，报告循环内重复 IO、重复查询、全表扫描、批量未分批、无界增长、忙等和无超时。不能凭“可能慢”或“以后会扩展”报告中高风险。

## 可维护性

检查有实际维护影响的重复代码、逻辑冲突、多余逻辑、单一职责破坏、模块耦合、硬编码和死代码。单纯风格偏好不作为中高风险问题。

## 需求冲突

当需求与代码明确冲突时，允许报告需求不符合（REQUIREMENT_MISMATCH），并同时给出需求引用与代码位置。

## 风险与定位

没有准确文件位置和可核验证据的中高风险结论不成立，不得保持 MEDIUM、HIGH 或 CRITICAL。

## 输出约束

- 输出必须符合规定的 JSON Schema。
- 除代码、符号和路径外，报告文本使用简体中文。
